# New company onboarding

Part of the Evertrust Books accounting skill. The core rules in SKILL.md always apply.

## New company onboarding: browser → Manager → MCP

Use this workflow when asked to create a company/business/file in Manager and connect it to Evertrust Books, including batch requests for missing clients. Creating an empty business does not import transactions or configure its accounting policies.

1. **Reconcile before creation.** Read the authorized client source (for example SharePoint Client Information), the complete Manager business list and MCP `list_connections`. Follow pagination. Compare legal names, aliases and available registration identifiers; folder names alone do not establish distinct entities. Distinguish an absent Manager business from an existing business with no MCP connection. Do not duplicate businesses for spelling variants, missing tokens or an interrupted run. Flag ambiguous identities and archived/closed clients rather than automatically activating them. If source access is incomplete, state the coverage limitation instead of claiming all missing clients were found.
2. **Establish scope.** Keep a per-company checklist of source identity, existing Manager business, existing MCP connection and intended action. A request to create the named missing businesses and put their tokens into MCP authorizes that workflow; do not repeatedly ask for the same scope. Follow the active browser host's credential-creation and login requirements when they require a separate native approval. Reuse confirmed approval only within its actual scope; never bypass a required approval or infer it from silence.
3. **Create only missing businesses.** Use the browser skill and the current observed Manager UI on the authorized instance. Do not guess URLs, selectors or unsupported MCP business-creation endpoints. Create the requested empty business, then reread the business list and open it to verify the selected identity. Preserve existing companies. Do not add transactions, COA templates, opening balances, currency/tax settings or other accounting configuration without authorization and evidenced values.
4. **Create and capture a company token.** Inspect the selected business's actual API/access-token UI. Use a recognizable token name such as Evertrust Books where the UI supports naming; distinguish Manager's token name from the optional MCP label. Confirm the token belongs to the intended business and use only the requested access scope. Handle secrets through the approved credential/browser flow. Never echo tokens/passwords into chat, screenshots, logs, skill files, source commits or audit attachments. Do not create another token simply because a later save/test failed; first reconcile what already exists.
5. **Save into the existing MCP service.** Open the authorized Evertrust Books company-connections page. Reuse its signed-in session or supported secure login flow; never retrieve or print hosting environment secrets to bypass login. Check existing connections again, use Add connection for a genuinely new connection, enter the Manager token in the token field and the optional identifying label below it, then save. Use the existing connection's edit flow only for an authorized replacement. Preserve other connections and service ownership. Do not invent an MCP tool for connection administration when none is advertised.
6. **Verify every company independently.** Confirm saving succeeded, inspect the returned business identity, and run that connection's Test action. Refresh `list_connections` and use a supported read with the exact returned `connection_id` when available. Record whether each stage is business-created, token-created, connection-saved, test-passed or pending. A saved token is not a passed test; an empty GL is not proof of a working connection. If browser testing passes but MCP tools cannot yet see the connection, report the distinction and reconcile session/owner visibility.
7. **Checkpoint and resume safely.** For batches, complete and record stages per company. After timeouts or interruption, reread both systems before continuing. Resume only missing stages; never recreate a confirmed business, token or connection merely to restart. On an identity mismatch or uncertain result, stop that company's writes, reconcile it and continue independent authorized companies when possible. Do not delete businesses or revoke tokens as automatic rollback.
8. **Report verified results.** Summarize companies created/reused, connections saved, tests passed and unresolved items, with per-company status when outcomes differ. State explicitly that these are empty businesses and no transactions were entered when applicable. Keep evidence free of credentials. Store operational connection/token data in the service's encrypted connection store, never in GitHub. Commit only reusable instructions/code when asked to synchronize the Skill; source synchronization alone does not prove the deployed service has refreshed its Skill.
