# Corrections, batch changes, migrations and journal openings

Part of the Evertrust Books accounting skill. The core rules in SKILL.md always apply.

## Cross-module migration execution

- Before the first financial write, prepare the connected plan: source and destination records, retained journal lines, exact deletions, subsidiary/invoice links, settlement amount changes and expected accounting differences. Obtain any missing specific authorization together before creating temporary duplicates; reuse it across unchanged execution chunks. Source conflicts remain unresolved until the user's confirmed source-priority rule or further evidence resolves them.
- Keep one current external checkpoint of source/destination keys, current hashes, completed creates, verified changes and remaining work. Reconcile live records before resuming; old reports and deleted reversal keys are historical evidence, not the current execution state. Complete creations before capturing a ledger-bound change preview, then apply that preview without intervening unrelated accounting writes. Never repeat a confirmed or uncertain create.
- Verify the new document's stored fields, principal/VAT/total, source-journal cleanup, party settlement and relevant inventory quantities/costs. Reconcile complete GL movements against the expected corrections, distinguishing evidenced control-account transfers from actual changes. A saved invoice alone does not establish a completed migration; disclose any temporary duplicate, unpaid balance or unconnected quantity/cost stage.

## Explicit links, errors and corrections in batches

- Use `resolve_record_links` for up to ten explicit same-company resource/key or exact-reference lookups. Only direct form reads or complete unique-reference scans return a usable native key/hash. Ambiguous or incomplete results remain unresolved. A reference match is lookup evidence; it does not establish a native link from a GL row.
- Raw `get_transactions` can opt into `resolve_account_candidates:true`. Exact matches against the complete same-company chart are returned separately under `account_resolution`; native `account_key`, `source_key` and native linkage statuses remain unchanged. Duplicate labels are ambiguous. Do not promote candidates to native transaction identities.
- On any tool call inspect both JSON-RPC `error` and `result.isError`, plus `structuredContent.status`, `verified` and `reconciliation_required`. An HTTP 200 response or saved JSON file does not mean an accounting operation succeeded. Validation errors return `argument_details` with required/allowed argument names and suggestions, without echoing supplied values. Read `get_tool_contract` for exact deployed input names.
- For multiple authorized corrections, prefer `prepare_record_changes` and inspect its immutable before/after preview, then call `apply_record_changes` with its `task_id` and `preview_hash`. Each update/delete needs the hash read from the specific original form; creates/imports are intentionally excluded. Use direct edits when requested; do not add reversing journals by default. A task hash binds the preview and does not replace human authorization. Existing user authorization for the exact changes does not require a second confirmation.
- Batch execution preflights every original record before dispatching writes, checkpoints before each dispatch, verifies each result and stops on failure or uncertainty. It is not atomic and never automatically rolls back or replays a claimed/stopped task. Use `get_record_change_task` and inspect actual records after interruptions; prepare only the remaining specifically authorized changes as a new task. Do not repeat uncertain writes.
- An optional `ledger_check` accepts explicitly chosen native scalar `group_by` and numeric `sum_fields`, with `expect_unchanged` and an optional absolute tolerance (0..0.01). It compares generic complete GL sums before and after, not financial-statement balances, native inventory quantities or invoice allocations. Choose dimensions/currency using actual evidence. Same-total concurrent edits cannot be detected. A failed/mismatched final check requires review and must not trigger a second execution.

Prefer `get_transactions(source:"general_ledger", auto_paginate:true)` for analyses accurately derivable from native GL. The connector internally follows `/transactions` pages; do not make the assistant retrieve 20 separate pages. Existing summary page mode remains compatibility-only and is not a substitute for complete GL.

Use `from_date` / `to_date` for inclusive local native-date filtering, `filters` for exact scalar native-field matches (for example the evidenced `account` value), and `term` only when advertised upstream. Division/party filtering requires an actual returned native field; do not guess a query parameter or derive it from descriptions.

For compact results, supply generic `group_by` (native scalar field names, plus `month` derived from native date) and `sum_fields` (evidenced numeric fields). Examples: GL account movement summary uses `group_by:["account"], sum_fields:["amount"]`; monthly account movements uses `["account","month"]`. MCP performs generic transport/reduction; this Skill chooses grouping, interpretation, classification and reconciliation. Do not add a separate tool for every summary.

- Inspect `complete`, `result_complete` when present, `stop_reason`, `rows_read`, `total_records`, and `aggregation_performed`. Incomplete reads must never be presented as complete reports. Generic aggregation is withheld on pagination failures, bounds, changed totals or repeated pages. Raw results may be withheld when too large; request compact grouping. Live offset pagination cannot detect all concurrent edits: reconcile or rerun if live changes are suspected.
- GL requests all fields advertised by the native fields enum, preserves native debit/credit money objects and adds explicit linkage statuses. Native `/transactions` can still expose only account display labels and omit source keys even when references are available. A reference is lookup evidence, not stable source identity. Keep labels explicitly identified as labels. Bind COA classification only through verified unique matches to current native IDs; ambiguous or unmatched rows remain unresolved. Do not invent stable account IDs or document links.
- Account `amount` sums are signed movements. Establish native sign convention before converting to Debit/Credit. Net amounts alone do not necessarily prove gross debit and credit turnover; use native gross fields or a verified per-row posting convention. Never invent those columns.
- A GL Summary may report evidenced account movements. Monthly expenses/P&L require evidenced COA report classification, dates and currency. Customer revenue requires actual party dimensions or reconciled invoice links; GL labels alone are insufficient.
- TB and BS require verified opening/starting balances, period cutoff, retained earnings/tax/control-account semantics and all relevant postings. Period movement is not closing balance. Avoid double-counting openings already included in the feed; check total debits/credits only when the native data supports that calculation. AR/AP aging requires invoice dates, allocations, outstanding balances and cutoff; net GL is insufficient.
- Preserve native currencies; never sum mixed currencies without an evidenced conversion/base amount. Generic sums use floating point: round once to evidenced currency precision and reconcile material differences. State company, period, filters, source, completeness and unresolved semantics.

`list_report_interfaces`, `read_report_endpoint`, report-definition forms and `get_financial_report_data` remain compatibility/diagnostic interfaces, not the normal reporting workflow. Definitions (`*-form`) are configuration, not statements; legacy feeds/balance lists have `full_report:false`. If GL and document data lack required evidence, disclose it and request the relevant native export for reconciliation. Do not claim a native report interface is operational based on OpenAPI discovery alone.

## Journal openings and control-account adjustments

Use the user's authorized journal treatment for opening balances, stock additions and adjustments. Prefer editing the original journal when requested: replace only the relevant manual-account lines, preserve the other lines, date/reference and intended totals, and do not add a duplicate opening.

1. In the native journal, select the corresponding control account and inspect the fields it exposes. Complete the applicable subsidiary links and other fields from evidence. A line can be saved while its subsidiary is Suspense or blank; that is not proof of a correct module posting. Bind actual native IDs, not names or descriptions, and learn field names from the current UI/schema and a saved same-company form.
2. Distinguish the journal's optional Item/Qty display columns from account-specific fields. Expand the columns to inspect existing data when useful, but do not infer accounting effect from their checked state or invent enablement flags. Generic fields can persist without an immediately verified module result.
3. Verified native examples on Manager 26.10.10.0: the cash control-account line uses Account plus BankOrCashAccount and the debit/credit amount; selecting the bank subsidiary moved the existing opening value into the Bank and Cash Accounts module. Inventory opening debit lines stored Account for Inventory on hand, Item, positive Qty and Debit per product; native UI Update and subsequent module reads established the opening quantities and values. These fields are evidence for those flows, not defaults for unrelated accounts; inspect other adjustment directions and module fields rather than guessing.
4. Verify both the complete saved journal and the linked module. Reconcile the expected quantity/value or subsidiary balance, the old manual account, GL/Suspense and unchanged other postings. HTTP success, retained JSON, a balanced journal or visible columns alone are insufficient. If module totals disagree, inspect/reconcile the current document before another write; never repeat an uncertain create or add a second opening to make totals appear correct.
5. Inventory openings and outgoing cost are separate stages. Reuse existing item-linked purchases, link evidenced sales quantities while preserving invoice amounts/VAT/settlements, then run the native Recalculate workflow for the authorized scope and inspect its proposals. Verify resulting item quantities, inventory value and invoice costOfSales before removing the corresponding old manual cost postings through authorized direct edits. Preserve specifically unassigned product lines and their evidenced manual cost as an explicit unresolved exception; do not guess their item or claim a complete quantity reconciliation.

Keep before/after evidence and module reconciliation outside business descriptions. Record only tested behavior in this Skill; a native-UI outcome does not prove an automated API recalculation endpoint.
